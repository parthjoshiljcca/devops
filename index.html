How to read this manual

Every lab opens with Prerequisites & dependencies (what must already be true before you start) and a Concept section, and closes with What can go wrong (the situations you will actually hit in a lab room full of thirty laptops) and a Checkpoint (how to prove to yourself it worked). In between sits the hands-on work itself — sometimes one Step-by-step walkthrough, sometimes a few more specifically named subsections when a lab has more than one moving part (e.g. Lab 4's separate steps for starting a feature versus cutting a release). Read the "What can go wrong" sections even if your run goes cleanly — that is where the exam questions live.

Commands are shown with a $ prompt for Bash (Linux, macOS, Git Bash / WSL on Windows) and a PS> prompt only where PowerShell genuinely differs. If you are on Windows and using Git Bash, treat every $ block as yours verbatim.

A running example ties the labs together: a fictional repo called campus-events, owned by you, with a collaborator called Priya. By Lab 5 you and Priya will deliberately collide on the same line of the same file, because watching a conflict happen on purpose is the only way to stop fearing it.

1Install and Configure Git on Linux/Windows

Prerequisites & dependencies

  • Administrator/sudo rights on the machine (installers need them).
  • A working internet connection for the download, and later for git config --global credential.helper to reach GitHub.
  • Nothing depends on this lab having a GitHub account yet — that's Lab 2. Git itself works with zero network access; it is a local tool first and a networked one second. Keep that distinction in your head, it explains a lot of later behaviour (e.g. why git commit never touches the internet but git push does).

Concept

Git is not GitHub. Git is the version-control engine that runs entirely on your machine, tracking snapshots of a project in a hidden .git folder. GitHub is one of several hosting services (GitLab, Bitbucket, Gitea, Azure DevOps are others) that store a copy of that .git history remotely and add collaboration features — pull requests, issues, branch protection — on top. Confusing the two is the single most common source of "why doesn't this command talk to the internet" confusion in a first lab.

Step-by-step

Linux (Debian/Ubuntu family):

$ sudo apt update
$ sudo apt install git -y
$ git --version
git version 2.43.0

Linux (Fedora/RHEL family):

$ sudo dnf install git -y

Windows: Download the installer from git-scm.com/download/win. Run it and accept the defaults except two screens worth pausing on: - "Adjusting your PATH environment" — choose "Git from the command line and also from 3rd-party software" so git works in any terminal, not only Git Bash. - "Configuring the line ending conversions" — choose "Checkout Windows-style, commit Unix-style line endings" (this sets core.autocrlf=true). This one setting prevents an entire category of "the whole file shows as changed" false-conflicts you'll otherwise hit the moment you collaborate with a Linux/macOS teammate. We revisit this exact setting in Lab 5.

The installer also gives you Git Bash, a Bash-compatible terminal. Use it for this course unless told otherwise — it makes every command in this manual copy-paste identical across operating systems.

macOS (for completeness, not in the original brief but worth knowing): xcode-select --install gives you a minimal Git, or brew install git gives you a current one. Homebrew's is preferred; Apple's bundled Git lags behind.

First-time configuration (all platforms, run once per machine)

$ git config --global user.name "Parth Joshi"
$ git config --global user.email "you@example.com"
$ git config --global init.defaultBranch main
$ git config --global core.editor "code --wait"   # or "vim", "nano" — whatever you actually know

Why each line matters: - user.name / user.email are stamped into every commit you ever make, permanently, as plain text — not authentication, just attribution. The email should match the one on your GitHub account (Lab 2) or GitHub won't link your commits to your profile and they won't show up on your contribution graph. You can hold different name/email pairs per-repository with a local (non --global) config, useful if you use one identity for coursework and another for a job. - init.defaultBranch main fixes the name Git gives a brand-new repo's first branch. Old Git defaulted to master; GitHub, GitLab and the wider ecosystem standardized on main years ago. Set this once so you never see master again. - core.editor decides what opens when a command needs a text message from you without -m (an interactive rebase in Lab 9, an unresolved merge commit in Lab 5, git commit with no -m flag). If you skip this, Git falls back to vi, which strands a surprising number of students who don't know :wq exits it.

Verify everything landed:

$ git config --list --show-origin

Dependency graph for this lab

Everything else in this manual assumes Lab 1 is done exactly once per machine, not once per repo. user.name/user.email with --global apply to every repository you touch on that machine forever, until overridden locally.

What can go wrong

  • git: command not found after installing on Windows. You skipped the PATH screen, or you're using an old terminal window opened before the install — PATH changes only apply to new shells. Close and reopen the terminal; if still broken, re-run the installer and pick "Git from the command line and also from 3rd-party software."
  • Commits show the wrong author. You set config in the wrong scope — a per-repo (--local, the default when you omit --global) setting was made in one repo and you assumed it was global. git config user.email (no --global) inside a repo shows what will actually be used there; git config --global user.email shows the machine-wide fallback. Local always wins over global.
  • Line-ending churn ("every file shows as modified" the moment you git status after a fresh clone). core.autocrlf mismatch between your OS setting and the repo's .gitattributes (or lack of one). Fixed properly in Lab 5's "line endings" subsection — don't just git config core.autocrlf false and move on, that just relocates the problem to your collaborators.
  • vim opens and you can't get out. Press Esc then type :wq and Enter. Better: set core.editor as shown above so this never happens again.

Checkpoint

git --version prints a version ≥ 2.30, and git config --global --list shows your name, email, and init.defaultBranch=main.

2Create a GitHub Repository and Clone It Locally

Prerequisites & dependencies

  • Lab 1 complete (Git installed and configured).
  • A GitHub account, with the email matching git config --global user.email (see Lab 1's rationale).
  • Authentication set up — this is the part students skip and then get stuck on for twenty minutes. GitHub retired password authentication for Git operations in 2021. You need one of:
  • HTTPS + a Personal Access Token (PAT): GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens. Generate one scoped to the repos you need, with at least Contents: Read and write. When Git prompts for a password over HTTPS, you paste the token, not your account password.
  • SSH keys: generate once per machine with ssh-keygen -t ed25519 -C "you@example.com", then add the public key (~/.ssh/id_ed25519.pub) to GitHub → Settings → SSH and GPG keys. Test with ssh -T git@github.com — a successful response greets you by username, it does not drop you into a shell (that's expected, not an error).
  • GitHub CLI (gh auth login): the easiest for a lab room — it handles the token exchange interactively and stores credentials for you.

SSH vs. HTTPS is a real decision, not a coin flip: SSH needs no token to babysit (it just works once the key is registered) but is sometimes blocked on locked-down corporate/campus networks that only allow port 443; HTTPS works everywhere port 443 works but tokens expire and need rotating. This manual uses HTTPS in examples because it is the more common default; swap the URL scheme if you've set up SSH.

Concept

"Create a repository" happens in two independent places that must then be linked: GitHub creates a remote, empty (or template-seeded) repository; your machine has a local working copy. git clone is the single command that does both the "connect" and the "download everything" steps at once. The alternative — git init locally then git remote add — is for when the local folder already exists and you're retrofitting version control onto it (that's exactly what Lab 3 walks through, so you see both directions).

Step-by-step

  1. On github.com, click New repository. Name it campus-events. Tick Add a README file — this seeds the repo with one commit and the main branch, so the remote is never truly "empty" (an empty remote has no branches at all, which trips up git push the first time — seeding avoids that entirely for this lab).
  2. Choose visibility (Public/Private) and, optionally, a .gitignore template and license — both can be added later, so don't stress over this now.
  3. Copy the clone URL. Click Code → HTTPS (or SSH if you set that up) → copy.
  4. Clone it locally:
$ git clone https://github.com/<your-username>/campus-events.git
$ cd campus-events
$ git remote -v
origin  https://github.com/<your-username>/campus-events.git (fetch)
origin  https://github.com/<your-username>/campus-events.git (push)

origin is just a conventional name for "the remote I cloned from" — nothing forces that name, but every tutorial, every default flag, and every teammate will assume it, so don't rename it without a reason.

What can go wrong

  • remote: Support for password authentication was removed. You typed your GitHub account password when prompted. Use a PAT (HTTPS) or switch to SSH — see Prerequisites above.
  • Permission denied (publickey) over SSH. Either no key is registered on GitHub, the wrong key is being offered (ssh -T git@github.com -v shows which key file it tried), or the key was never added to the ssh-agent. Run ssh-add ~/.ssh/id_ed25519 and retry.
  • Cloning into a folder that already has a campus-events directory. Git refuses ("destination path already exists and is not an empty directory") rather than merge into it. Remove or rename the existing folder, or clone with an explicit target: git clone <url> campus-events-2.
  • Corporate/campus firewall blocks SSH (port 22). Switch to HTTPS, or configure SSH over the 443 port trick (Host github.com / Hostname ssh.github.com / Port 443 in ~/.ssh/config) — worth knowing exists, rarely needed in a teaching lab.
  • Cloned the wrong branch / repo is huge. git clone --branch <name> --single-branch <url> clones just one branch; git clone --depth 1 <url> grabs only the latest snapshot's history — a shallow clone. Fine for a quick look, but several later commands (rebase across history, git log of old commits, some merge scenarios) behave oddly on a shallow clone until you git fetch --unshallow. Don't shallow-clone a repo you intend to develop in for the rest of this course.

Checkpoint

git remote -v inside the folder shows origin pointing at your GitHub URL, and git log --oneline shows the initial README commit.

3Perform Basic Git Operations (init, add, commit, push, pull)

Prerequisites & dependencies

  • Either Lab 2's cloned campus-events folder, or a fresh local folder you're about to turn into a repo with git init (both paths are shown below — know when to use each).
  • Push requires the authentication from Lab 2's prerequisites to actually be working, even though init/add/commit need no network at all.

Concept: the three (really four) trees

Every Git operation moves a change through a strict pipeline:

  1. Working directory — the actual files on disk, as your editor sees them.
  2. Staging area / index — a draft of the next commit. git add copies a file's current state here. Crucially, staging is a snapshot: if you edit the file again after git add, the working directory and the index now disagree, and git status will tell you so, and you'll need to git add again to include the new edit.
  3. Local repository (.git history) — git commit seals whatever is in the staging area into a permanent, addressable snapshot with a SHA-1/SHA-256 hash, a message, an author, and a timestamp. This is 100% local — no network involved, no matter how many git commits you make.
  4. Remote repository — GitHub's copy. git push uploads local commits there; git pull downloads and integrates remote commits you don't have yet.

This four-stage pipeline is the mental model for the entire course. Every future "what does X do" question reduces to "which of these four stages does it touch."

Two ways to start a repo

A. Retrofitting version control onto an existing folder (git init):

$ mkdir campus-events-notes && cd campus-events-notes
$ git init
Initialized empty Git repository in .../campus-events-notes/.git/
$ git remote add origin https://github.com/<you>/campus-events-notes.git

git init alone creates only the local repo — there is no remote yet, hence the manual git remote add. This is the path you use when a project already exists on disk (or when you created the GitHub repo without a README, leaving it genuinely empty) and you're wiring the two together yourself, one step at a time, instead of letting clone do both.

B. Already have it from git clone (Lab 2) — init and remote add already happened for you; skip straight to the daily loop below.

The daily loop

$ echo "# Campus Events" > README.md          # working directory change
$ git status                                   # see what changed
$ git add README.md                            # stage it (or `git add .` for everything)
$ git status                                   # now shows "Changes to be committed"
$ git commit -m "docs: initialize project README"
$ git push origin main                         # upload to GitHub
$ git pull origin main                         # download + merge teammates' work

git status is not optional ceremony — run it before every add/commit/push in this course until it's muscle memory. It is the only command that tells you, truthfully, which of the four stages each file currently sits in.

git add in more detail

  • git add <file> — stage one file.
  • git add . — stage everything changed/new in and below the current directory.
  • git add -p — patch mode, walks you through each changed hunk and asks whether to stage it. This is how you write clean, single-purpose commits out of a messy working session — stage only the hunks that belong to one logical change, commit, then stage the rest separately. Professional teams live in -p.
  • git add -u — stage modifications and deletions but not new untracked files.

git commit in more detail

  • git commit -m "message" — the common case.
  • git commit (no -m) — opens core.editor (Lab 1) for a longer message: a short summary line, a blank line, then a wrapped body explaining why, not what (the diff already shows what).
  • git commit --amend — replaces the most recent commit with a new one (new message and/or newly staged changes folded in). Only amend commits that have not been pushed, or that you are certain nobody has already pulled — amending rewrites history, and rewritten history that others have built on top of causes the diverged-history pain described in Lab 9.
  • git commit -am "message" — shortcut that stages tracked, modified files and commits in one step. It will not pick up brand-new untracked files — a classic gotcha when a student swears they committed a new file and it isn't on GitHub.

git push in more detail

$ git push origin main

origin = which remote, main = which local branch, pushed to the branch of the same name on the remote by default. The first push of a brand-new local branch needs -u (--set-upstream) once:

$ git push -u origin feature/rsvp-list

This records that your local feature/rsvp-list branch tracks origin/feature/rsvp-list, so every push/pull after that can drop the arguments entirely and just be git push / git pull.

git pull in more detail

git pull is shorthand for two steps done together: git fetch (download remote commits into a local "remote-tracking branch" like origin/main, without touching your working directory) then git merge origin/main (integrate those commits into your current branch). Because it merges, a git pull can itself produce a merge conflict (Lab 5) or open a merge-commit-message editor. Some teams prefer git pull --rebase, which does fetch + rebase instead of fetch + merge — the difference, and when to prefer each, is the entire subject of Lab 9.

What can go wrong

  • git push rejected: "Updates were rejected because the remote contains work that you do not have locally." Someone else pushed since you last pulled. Run git pull (resolve any conflict per Lab 5) then push again. Never reach for git push --force to make this go away — that overwrites your teammate's work on the server.
  • nothing to commit, working tree clean when you know you changed a file. Either the file is listed in .gitignore (check with git check-ignore -v <file>), or you edited it after staging and forgot to git add again, or you're in the wrong directory/repo entirely — git status at the top always tells you which branch and which repo you're in.
  • Committed a file you didn't mean to (e.g. a .env with secrets). git rm --cached <file> un-stages/un-tracks it for future commits and add it to .gitignore — but the secret is still in history from the earlier commit. If it's already pushed, treat the secret as compromised: rotate it. Purging it from history (git filter-repo, or GitHub's secret-scanning remediation) is possible but out of scope for a first lab — prevention via .gitignore from day one is the real fix, covered again in Lab 10.
  • Detached HEAD after checking out a specific commit hash instead of a branch. You're no longer "on" any branch; commits you make here aren't attached to anything and can be lost once you switch away. git status will say HEAD detached at <hash> — get back to safety with git checkout main (or git switch main), and if you made commits you want to keep, git branch temp-fix before switching, while still detached, to give them a name.
  • git pull opens an editor unexpectedly. That's the merge-commit message editor (see git pull above) — save and close it (or set git config pull.rebase false/true explicitly so Git stops warning you every time about the ambiguous default).

Checkpoint

git log --oneline --graph shows your commits; git status reports "working tree clean"; the same content is visible on github.com after git push.

4Create and Merge Feature Branches Using GitFlow

Prerequisites & dependencies

  • Lab 3's daily loop, fluently.
  • A repo with at least two long-lived branches conceptually planned (main, develop) — GitFlow does not work with a single-branch repo, so this lab includes creating that structure.

Concept

A branch is nothing more than a movable pointer to a commit — creating one is instant and cheap (unlike, say, copying a whole folder) because Git doesn't duplicate any files; it just writes a 41-byte pointer. GitFlow is a branching model — a convention for what branches exist and what they're for — not a Git feature. Vanilla Git has no idea what "GitFlow" is; it's enforced entirely by team discipline (or by the git-flow extension tool, which just automates the same commands you're about to run by hand, so we do it by hand first so the model is transparent).

GitFlow's branches, and their jobs: - main — always reflects production/released code. Every commit on main is, in principle, deployable. - develop — the integration branch. Finished features land here first, before they're bundled into a release. - feature/* — one branch per feature, branched from develop, merged back into develop when done. Never merged directly into main. - release/* — cut from develop when preparing a release (version bump, final bug fixes, no new features); merged into both main and back into develop when done, then tagged (Lab 7). - hotfix/* — branched from main for an urgent production fix that can't wait for the next release cycle; merged into both main and develop, tagged.

GitFlow is deliberately heavyweight — it suits projects with scheduled releases. Lighter alternatives (GitHub Flow: just main + short-lived feature branches, deploy on every merge; Trunk-Based Development: everyone commits to main behind feature flags) exist and are worth knowing by name even though this lab teaches GitFlow specifically, because a job interview is as likely to ask "which model would you use for a SaaS product deployed daily" (answer: probably not GitFlow) as it is to ask you to define GitFlow.

Step-by-step

1. Establish develop (one-time, per repo):

$ git checkout main
$ git pull
$ git checkout -b develop
$ git push -u origin develop

checkout -b <name> = create the branch and switch to it in one step (equivalent to git branch <name> then git checkout <name>; modern Git spells this git switch -c <name>, which is the same operation under a friendlier, purpose-built command — checkout historically did too many unrelated things at once, which is why switch/restore were split out of it).

2. Start a feature:

$ git checkout develop
$ git pull
$ git checkout -b feature/rsvp-list

Always branch features from an up-to-date develop, not from whatever your develop happened to be yesterday — git pull first, every time, is the habit that prevents half of Lab 5's conflicts before they happen.

3. Work, commit, push the feature branch (own remote branch, tracked independently):

$ echo "RSVP list feature" >> features.md
$ git add features.md
$ git commit -m "feat(rsvp): scaffold RSVP list page"
$ git push -u origin feature/rsvp-list

Pushing a feature branch is optional strictly speaking (you could keep it fully local until it's finished) but is good practice: it backs your work up, and it's required if you want to open a Pull Request (Lab 6) or let a teammate see/pull your branch.

4. Merge the finished feature back into develop:

$ git checkout develop
$ git pull
$ git merge --no-ff feature/rsvp-list
$ git push

--no-ff (no fast-forward) is the detail that makes GitFlow work as documented. Without it, if develop hasn't moved since you branched, Git will happily just slide the develop pointer forward to your last feature commit — a fast-forward merge — which leaves no trace that a feature branch ever existed; your git log --graph looks like a straight line. --no-ff forces Git to create a real merge commit with two parents even when a fast-forward was possible, preserving the branch structure in history — which is the entire point of GitFlow's model being visible later in git log --graph. (Contrast this with rebase's philosophy in Lab 9, which deliberately erases that branch structure in favor of a straight line — the two techniques encode opposite values about what history should look like, and GitFlow explicitly picks --no-ff merges.)

5. Clean up:

$ git branch -d feature/rsvp-list          # delete local branch (only if merged)
$ git push origin --delete feature/rsvp-list

-d (lowercase) refuses to delete a branch with unmerged commits, protecting you from silently losing work; -D (uppercase) forces it — use -D only when you are certain the branch's commits are genuinely disposable (e.g. an abandoned experiment).

6. Release:

$ git checkout develop
$ git checkout -b release/1.1.0
# final polish commits, version bump, changelog
$ git checkout main
$ git merge --no-ff release/1.1.0
$ git tag -a v1.1.0 -m "Release 1.1.0"      # see Lab 7 for full tag/semver discussion
$ git push origin main --tags
$ git checkout develop
$ git merge --no-ff release/1.1.0
$ git push origin develop
$ git branch -d release/1.1.0

7. Hotfix (urgent production bug, can't wait for the next release):

$ git checkout main
$ git checkout -b hotfix/1.1.1
# fix, commit
$ git checkout main
$ git merge --no-ff hotfix/1.1.1
$ git tag -a v1.1.1 -m "Hotfix 1.1.1"
$ git push origin main --tags
$ git checkout develop
$ git merge --no-ff hotfix/1.1.1
$ git push origin develop
$ git branch -d hotfix/1.1.1

Merging a hotfix into both main and develop is the step students most often forget — skip it and the fix silently disappears from the next regular release, only to "reappear" as a bug that was supposedly already fixed.

What can go wrong

  • Branched feature/x from main instead of develop by mistake. The feature will carry an unrelated history and complicate the eventual merge into develop. Fix early: git rebase --onto develop main feature/x (moves just your feature's commits onto develop) — better to just re-branch from the right base if you haven't done much work yet.
  • Two people branch feature/rsvp-list off the same name independently. GitHub allows duplicate branch names to collide only if pushed to the same remote ref — Git will simply refuse the second person's push as a non-fast-forward rejection (same message as Lab 3's push-rejected case) because the branch already exists remotely with different commits. Rename one branch (git branch -m new-name) before pushing.
  • Merge conflict during git merge --no-ff. Entirely normal and expected in a multi-person repo — this is what Lab 5 is dedicated to.
  • Forgot --no-ff and now git log --graph shows no branch structure. Not fatal, just cosmetic/informational loss for future readers; nothing to "fix" retroactively, just remember it next time. (You cannot cleanly turn a fast-forward merge into a "fake" merge commit after the fact without rewriting history.)
  • Deleted a feature branch locally, but it still exists on GitHub (or vice versa). git branch -d and git push origin --delete are two separate operations against two separate copies of the branch; you need both. git fetch --prune cleans up local references to branches that were deleted on the remote.

Checkpoint

git log --graph --oneline --all shows a clear diamond shape where the feature branch diverged from and rejoined develop; git branch -a no longer lists the merged-and-deleted feature branch (after a --pruned fetch).

5Resolve Merge Conflicts Using Git Tools

Prerequisites & dependencies

  • Lab 4's branching fluency — you need two branches with real divergent history to get a real conflict, not a staged one.
  • Understand that a conflict is not an error state and not a sign anything is "broken" — it's Git honestly telling you it cannot guess your intent and needs a human decision.

Concept: why conflicts happen at all

Git's merge algorithm (a three-way merge: your branch's tip, the other branch's tip, and their common ancestor) auto-resolves the overwhelming majority of merges with zero human input — different files changed, or different non-overlapping lines in the same file, merge silently. A conflict happens specifically when both branches changed the same lines of the same file differently since their common ancestor (or one branch edited a file the other deleted, etc.) and Git has no principled way to pick a winner.

Manufacturing a real conflict (do this deliberately, once, so you stop fearing it)

$ git checkout main
$ git checkout -b feature/edit-title
$ echo "Campus Events Portal" > README.md
$ git commit -am "docs: rename title (mine)"
$ git checkout main
$ git checkout -b feature/edit-title-2
$ echo "Campus Events Hub" > README.md
$ git commit -am "docs: rename title (Priya's, simulated)"
$ git checkout feature/edit-title
$ git merge feature/edit-title-2

Git stops and reports:

Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

Reading the conflict markers

Open the file — Git has written both versions into it, inline:

<<<<<<< HEAD
Campus Events Portal
=======
Campus Events Hub
>>>>>>> feature/edit-title-2
  • Everything between <<<<<<< HEAD and ======= is your current branch's version (the one you ran git merge from, i.e. the branch you were on).
  • Everything between ======= and >>>>>>> <branch-name> is the incoming branch's version — the one named after >>>>>>> is the one you're merging in.

git status during a conflict is your dashboard — it lists every file "both modified" (needs manual resolution) versus files Git already auto-merged cleanly.

Resolving it — three approaches, in increasing order of tooling

A. By hand, in any editor. Delete the marker lines, keep whichever content (or a hand-blended combination) is correct, save. This always works and requires no extra tooling — the only method guaranteed available in every environment.

B. With git mergetool, configured to a visual 3-way diff tool.

$ git config --global merge.tool vscode
$ git config --global mergetool.vscode.cmd 'code --wait $MERGED'
$ git mergetool

(VS Code has built-in 3-way merge UI once opened this way; other common choices are meld, kdiff3, vimdiff — git mergetool --tool-help lists what's detected on your machine.) The visual tool shows "ours," "theirs," and the merged result side by side, which scales far better than reading <<<<<<< markers once a conflict spans dozens of lines.

C. Resolve strategy shortcuts for the (rare, and slightly dangerous) case where you know an entire file should just be one side wholesale:

$ git checkout --ours  README.md    # keep entirely your side
$ git checkout --theirs README.md   # keep entirely the incoming side
$ git add README.md

Use these sparingly — "ours/theirs" is a blunt instrument for line-level conflicts; it's appropriate mainly for whole binary/generated files, not hand-edited prose or code where a real blend is usually correct.

Finishing the merge

Once every conflicted file is edited and staged:

$ git add README.md
$ git status              # confirm: "All conflicts fixed but you are still merging."
$ git commit              # opens editor pre-filled with a merge commit message — usually fine as-is
$ git push

You do not pass -m to this final commit in the normal case — Git already generated a sensible merge-commit message; just save and close the editor (or git commit --no-edit to accept it without even opening the editor).

Aborting instead

If you get partway through and realize you don't actually want this merge right now:

$ git merge --abort

This cleanly rewinds to exactly the state before you ran git merge — the only fully safe undo for a mid-conflict merge. Manually deleting marker lines and then changing your mind is much harder to undo cleanly.

The line-endings conflict — a special, very common case

If core.autocrlf (Lab 1) differs between collaborators, or a .gitattributes is missing, Git can report an entire file as conflicted/changed when only line endings differ, drowning the real change in noise. Fix at the repo level, once, with a .gitattributes file committed to the repo:

* text=auto
*.sh text eol=lf
*.bat text eol=crlf

This tells Git to normalize line endings on commit regardless of any individual contributor's core.autocrlf, which is more robust than relying on every teammate's personal Git config being correct.

Diff/merge algorithm dial

Beyond the default, Git supports alternate merge strategies for stubborn cases: git merge -X ours / -X theirs (prefer one side automatically only for hunks that would otherwise conflict — subtly different from checkout --ours which acts on whole files) and git merge -X patience / histogram (different diff algorithms, sometimes producing a cleaner, more intuitive conflict for code with repeated similar blocks, e.g. boilerplate-heavy code). Worth knowing these flags exist; you won't need them for a first lab conflict.

What can go wrong

  • Forgot git add after editing a conflicted file — git commit refuses with "fix conflicts and then commit the result," or worse, an old Git version might let a stray marker slip through uncommitted-staged. Always re-run git status before committing a resolved merge.
  • Left <<<<<<</=======/>>>>>>> markers in the committed file because you saved without deleting them. This is a silent, ugly bug — nothing stops you from committing broken-looking text/code. Discipline: always view the staged diff (git diff --staged) before the final commit and visually confirm no marker lines remain.
  • Binary file conflict (e.g. an image, a .docx, a .xlsx). Git cannot show inline markers for binary content — git status reports it conflicted, and you must pick one side wholesale with checkout --ours/--theirs (there is no "blend" for binary files) or manually replace the file with a hand-merged version from outside Git and git add it.
  • Conflict during git pull, not git merge directly. Same resolution process — recall from Lab 3 that pull is fetch + merge under the hood, so a pull-conflict is a merge-conflict wearing a different command name.
  • Conflict during git rebase instead of git merge. Markers look identical, but the resolution commands differ (git rebase --continue / --abort / --skip instead of commit/--abort) — covered fully in Lab 9. Don't run git commit mid-rebase; the workflow is different on purpose.
  • Merged the wrong direction (merged main into your feature branch when you meant the reverse). Not actually dangerous — merging is non-destructive to the source branch — but it does add "downstream" commits to your feature branch's history that a later PR diff will now include, confusing reviewers. If caught immediately and unpushed, git reset --hard HEAD~1 before the merge commit undoes it (only if the merge was the very last commit and nothing since).

Checkpoint

The manufactured conflict above is resolved, committed, and git log --graph shows a merge commit with two parent lines converging into it.

6Configure Branch Protection Rules and Pull Requests on GitHub

Prerequisites & dependencies

  • A GitHub repo with at least main and one other branch with real, different commits (Lab 4's develop/feature structure works perfectly).
  • Repository admin rights — branch protection is a settings-level permission; a plain "write" collaborator cannot configure it, only benefit from (or be blocked by) it.
  • If this is a free personal GitHub account, note that some protection features (e.g. requiring reviews from specific people on private repos) may be limited compared to a paid/organization plan — public repos get the full feature set free.

Concept

Everything up to now assumed direct pushes to shared branches are fine. In any real team, they aren't: branch protection turns main (and often develop) from "anyone can push directly" into "changes must arrive via reviewed Pull Request," and a Pull Request is GitHub's mechanism for proposing "please merge branch A into branch B" as a reviewable, commentable, checkable unit before the merge actually happens — distinct from git merge, which is the raw local/CLI operation with no review step at all.

Opening a Pull Request

$ git checkout -b feature/notifications
# work, commit, push
$ git push -u origin feature/notifications

On GitHub, a "Compare & pull request" banner appears; or manually: Pull requests → New pull request, base = develop (or main), compare = feature/notifications. Fill in a title and description (Lab 8 shows how a PR template pre-fills this), then Create pull request.

A PR is not a merge — it's a live, updating comparison. Every new commit pushed to feature/notifications while the PR is open appears in it automatically; nothing needs re-submitting.

Configuring branch protection

Settings → Branches → Add branch protection rule (or, in newer GitHub UI, Rulesets). Target pattern: main. Common rules, and what each actually buys you: - Require a pull request before merging — disables direct git push origin main; anyone pushing straight to main now gets remote: error: GH006: Protected branch update failed. - Require approvals (e.g. 1 or 2) — the PR's green "Merge" button stays disabled until that many reviewers click Approve. The PR author cannot approve their own PR by default. - Require status checks to pass before merging — ties into CI (e.g. a GitHub Actions workflow running tests/linters). Merge is blocked if the CI run is red, or even just still running. - Require branches to be up to date before merging — forces a stale PR (one whose base has moved since the PR's branch last synced) to be updated (merge or rebase the latest base in) before it's allowed to merge — prevents merging code that was never actually tested against the current main. - Require conversation resolution before merging — every open review comment thread must be marked resolved. - Require signed commits — every commit in the PR must carry a valid GPG/SSH signature (see the note on git tag -s in Lab 7 for the same underlying mechanism applied to tags). - Do not allow bypassing the above settings — closes the loophole where repo admins are otherwise exempt from their own rules by default; tick this for genuinely enforced protection. - Restrict who can push to matching branches — limits even branch creation matching the pattern to named people/teams — useful for protecting release/* naming too.

CODEOWNERS (.github/CODEOWNERS file, e.g. *.js @priya) combined with "Require review from Code Owners" auto-assigns and requires approval specifically from the person/team who owns the touched files — the standard mechanism for "only the payments team can approve changes to /payments/."

Reviewing a PR

As a reviewer: Files changed tab shows the diff; click a line to leave an inline comment; Review changes → Comment (no verdict, just discussion) / Approve / Request changes (blocks merge until addressed, distinct from a protection-rule-mandated approval count — Request Changes is itself a hard block regardless of settings, until the same reviewer or another approves).

Merging a PR — three button choices, and they are not equivalent

  • Create a merge commit — equivalent to local git merge --no-ff; preserves full branch history, adds one merge commit.
  • Squash and merge — flattens every commit on the feature branch into a single new commit on the base branch. Clean linear history on main, but the feature branch's individual commit-by-commit history is lost from main's log (it still exists on the now-orphaned feature branch until deleted). Popular for feature branches with messy "wip", "fix typo", "actually fix it" commit trails.
  • Rebase and merge — replays the feature branch's individual commits, one by one, directly onto the tip of the base branch, with no merge commit at all — a linear history and preserved individual commits. This is GitHub performing the same rebase operation Lab 9 covers by hand, server-side.

Which to pick is a team-policy decision, usually set as the only enabled option in Settings → General → Pull Requests so contributors aren't guessing each time. Squash is the most common default for feature-branch-heavy teams; merge commits suit GitFlow-style history (matches Lab 4's --no-ff philosophy exactly); rebase-and-merge suits teams that want linear history without losing granular commits.

What can go wrong

  • "This branch is out-of-date with the base branch" and the merge button is greyed out. The main/develop you branched from has moved on. Update the PR's branch: on GitHub, click Update branch (this merges the base into your branch — a real merge commit lands on your feature branch), or locally git checkout feature/x && git pull origin develop && git push.
  • Status checks stuck "Expected — Waiting for status to be reported." No CI workflow is actually configured to run on this repo/branch, so the required check can never report success — remove that specific required check or add the missing workflow.
  • You have admin rights and the "Merge" button works even though your own review requirement isn't met. "Do not allow bypassing" wasn't ticked — see above.
  • Reviewer approved, then the author pushed one more commit. Depending on settings, prior approvals may or may not be dismissed automatically ("Dismiss stale pull request approvals when new commits are pushed" is itself a protection option) — know which policy your repo uses so you don't assume a stale approval still covers new code.
  • Merge conflict shown directly on the PR page ("This branch has conflicts that must be resolved"). GitHub's web editor can resolve simple conflicts inline, but for anything non-trivial, resolve locally exactly as in Lab 5, then push — the PR updates automatically once the push lands.
  • Deleted the head branch immediately after merging, then needed a commit from it. The commits aren't gone (they exist in the merge commit's history on the base branch, and in GitHub's reflog/API for a while), but the branch name is gone — recreate it from the merge commit's parent if truly needed, or find the commit via git log on the base branch.

Checkpoint

main rejects a direct git push; a PR from feature/notifications merges only after the configured approvals and checks are satisfied, using whichever of the three merge strategies your repo policy specifies.

7Apply Semantic Versioning by Creating Git Tags and Releases

Prerequisites & dependencies

  • A repo with at least one meaningful commit you'd call "shippable" — tagging is meaningless on an empty repo.
  • Conceptual buy-in that a version number is a promise to consumers, not a vanity counter — this framing is what makes every SemVer rule below make sense instead of feeling arbitrary.

Concept: Semantic Versioning (SemVer)

A version is MAJOR.MINOR.PATCH (e.g. 2.4.1), optionally followed by a pre-release tag and/or build metadata (2.4.1-rc.1+build.20). The rule, precisely: - MAJOR increments when you make an incompatible/breaking API change. Anything depending on you must review before upgrading. - MINOR increments when you add functionality in a backward-compatible way. Safe to upgrade automatically; nothing that worked before stops working. - PATCH increments for backward-compatible bug fixes only — no new functionality, no behavior change other than "the bug is gone." - Once MAJOR is incremented, MINOR and PATCH both reset to 0 (and similarly MINOR resets PATCH to 0). - 0.y.z is special-cased by the spec as "initial development" — anything may change at any time, no compatibility promise implied yet. Version 1.0.0 is the declaration "the public API is now stable." - Pre-release versions (1.0.0-alpha, 1.0.0-beta.2, 1.0.0-rc.1) sort before their final release (1.0.0-alpha < 1.0.0) — useful for tagging release candidates that still need testing before the "real" tag.

Concretely: renaming a public function is MAJOR; adding a new optional parameter with a default is MINOR; fixing a crash without changing any signature is PATCH. This is a judgment call your team must apply consistently — SemVer is a convention, not something Git enforces for you.

Git tags: lightweight vs. annotated — the distinction that matters

$ git tag v1.0.0-lite                       # lightweight: just a name pointing at a commit
$ git tag -a v1.0.0 -m "Release 1.0.0"      # annotated: a full Git object with its own metadata

A lightweight tag is nothing more than a named pointer, like a branch that never moves — no author, date, or message of its own. An annotated tag is a real object in the Git database: it stores its own tagger name/email, date, and message, and (see below) can be GPG-signed. git describe, GitHub Releases, and most tooling that treats tags as meaningful release points expect annotated tags — use -a (or -s for signed) for anything you intend to actually publish as a release, and reserve lightweight tags for quick personal bookmarks.

Signed tags (extra assurance the tag genuinely came from you, not someone with push access to your repo):

$ git tag -s v1.0.0 -m "Release 1.0.0"
$ git tag -v v1.0.0        # verify a signature

Requires a GPG key configured (git config --global user.signingkey <key-id>) — worth mentioning, not required for this lab's checkpoint.

Pushing tags (they do not push automatically)

$ git push origin v1.0.0          # a single tag
$ git push origin --tags          # every tag not yet on the remote

This is the single most common tagging mistake: a student tags locally, confirms it with git tag, and wonders why it never shows up on GitHub — git push alone never pushes tags; you must say so explicitly.

Tagging retroactively, on an older commit

$ git log --oneline
$ git tag -a v0.9.0 <commit-sha> -m "Backfilled tag for 0.9 milestone"

Perfectly valid — a tag doesn't have to point at HEAD.

Creating a GitHub Release from a tag

A Release is GitHub's layer on top of a tag: a human-readable changelog, optional binary attachments (build artifacts, installers), and a dedicated page in the Releases sidebar. Releases → Draft a new release → choose an existing tag (or type a new one and let GitHub create it for you at "Publish") → title, description (GitHub can Generate release notes automatically from merged PRs since the last release, which pairs directly with Lab 10's commit-convention discipline — the cleaner your commit/PR titles, the better that auto-generated changelog reads) → Publish release.

Note the direction of dependency: you can create the tag via CLI first and attach a Release to it after, or let GitHub create the tag as a side effect of publishing a Release — either order works, but a Release without an underlying tag is not possible; a tag without a Release is completely normal (most tags in most repos never get a formal Release page).

What can go wrong

  • Tagged the wrong commit. Delete and recreate: git tag -d v1.0.0 (local) then git push origin :refs/tags/v1.0.0 (remote deletion — note the leading colon, "push nothing to this ref") then re-tag correctly and push again. If anyone already pulled the bad tag, warn them — tags are meant to be immutable pointers by convention, and silently moving a published tag is considered bad practice (some CI/CD systems cache artifacts by tag name and will now serve stale content).
  • Two people tag v1.0.0 independently before either pushes. Whoever pushes first wins; the second person's git push origin v1.0.0 is rejected because the tag ref already exists remotely with different history underneath it. Coordinate releases through one person/process, not ad hoc.
  • Used a lightweight tag for a real release, and git describe or a build script that expects annotated-tag metadata misbehaves. Delete and recreate as annotated (-a), as above.
  • SemVer disagreement on the team ("is adding a new REST endpoint MINOR or should it be MAJOR since old clients don't know about it?"). Adding a new, non-breaking endpoint is MINOR by the spec — old clients are unaffected, they simply don't use the new capability. MAJOR is reserved for changes that break existing callers.
  • Forgot --tags on push and thinks the release "vanished." It never left your machine — git tag locally still lists it; push it explicitly.
  • Version number skipped or went backwards because of a bad merge/rebase mixing release branches. Always confirm the intended version against git tag --list --sort=-v:refname (sorts tags by SemVer descending) before cutting a new one, rather than trusting memory.

Checkpoint

git tag --list -n shows an annotated v1.0.0 with its message; it's visible on GitHub under Tags, and a corresponding entry appears under Releases with generated notes.

8Create a CONTRIBUTING.md and Pull Request Template for a Repository

Prerequisites & dependencies

  • A repo with an established branching convention (Lab 4) and PR/review process (Lab 6) already decided — a CONTRIBUTING.md documents decisions you've already made, it doesn't make them for you. Write labs 4–7's policies down before writing this file, or you'll be inventing policy on the fly while writing docs, which usually produces inconsistent docs.

Concept

Two related but distinct files lower the friction (and raise the quality) of outside/team contributions: - CONTRIBUTING.md — prose documentation: how to set up the project locally, branch naming conventions, commit message conventions, how to run tests, how to submit a change, code style expectations. GitHub auto-links this file (a "Read the contributing guidelines" prompt) whenever someone opens an issue or PR, if it's placed in one of the recognized locations. - PR template — a form (or fixed checklist) that pre-populates the PR description text box the moment someone clicks "New pull request," so authors are prompted for the same structured information every time (what changed, why, how it was tested, linked issue) instead of a blank box that half of contributors leave nearly empty.

File locations GitHub recognizes (matters — wrong location = silently ignored)

Both files are recognized in any of: the repository root, a docs/ folder, or a .github/ folder — GitHub checks all three and uses whichever it finds first, in that order of visibility to users, but .github/ is the conventional choice for anything PR/issue-process-related, keeping the repo root uncluttered.

.github/
├── CONTRIBUTING.md
├── PULL_REQUEST_TEMPLATE.md
└── ISSUE_TEMPLATE/
    ├── bug_report.md
    └── feature_request.md

Writing CONTRIBUTING.md

A solid structure for a course/team project:

# Contributing to Campus Events

1. Fork or clone the repo.
2. `npm install` (or your project's actual setup command).
3. Create a branch off `develop`: `git checkout -b feature/<short-description>`.
## Branching model
We use GitFlow. `main` = production, `develop` = integration.
Branch prefixes: `feature/`, `release/`, `hotfix/`. See Lab 4 of the course manual.
## Commit messages
We follow Conventional Commits: `type(scope): short description`.
Types: feat, fix, docs, style, refactor, test, chore. See Lab 10.
## Submitting a change
1. Push your branch, open a PR against `develop`.
2. Fill in the PR template completely.
3. At least one approving review and a passing CI run are required to merge.
4. Squash-merge is our default; keep your branch's commits meaningful anyway,
   since they're visible during review even if squashed on merge.

Every section above answers a question a new contributor would otherwise have to ask in chat or guess wrong on — that's the actual test of whether a CONTRIBUTING.md is doing its job: could a stranger submit a correct first PR using only this file?

Writing .github/PULL_REQUEST_TEMPLATE.md

## What does this PR do?
## Related issue
Closes #
## Type of change
- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation
## How was this tested?
## Checklist
- [ ] My code follows the project's style guidelines

Closes #123 in a PR description is not just documentation — GitHub parses that exact syntax (Closes, Fixes, or Resolves followed by #<number>) and automatically closes issue #123 the moment this PR is merged, linking them permanently in both directions.

Multiple templates (larger repos)

GitHub supports several named templates in .github/PULL_REQUEST_TEMPLATE/ (plural, a folder) — e.g. feature.md, bugfix.md — selectable via a URL query parameter (?template=bugfix.md) or a chooser GitHub shows when more than one exists. Overkill for a single-team project; worth knowing for larger open-source repos with meaningfully different contribution types.

Committing and verifying

$ mkdir -p .github
$ git add .github/CONTRIBUTING.md .github/PULL_REQUEST_TEMPLATE.md
$ git commit -m "docs: add CONTRIBUTING guide and PR template"
$ git push

Verify by opening a new PR after this merges to develop/main — the description box should already contain the template text, not be blank.

What can go wrong

  • Template doesn't appear on new PRs. Wrong filename/location (must be exactly PULL_REQUEST_TEMPLATE.md, case-insensitive, in root/docs/.github), or it was only added on a feature branch and hasn't reached the default branch yet — GitHub reads the template from the PR's base branch, not the branch you're proposing.
  • CONTRIBUTING.md exists but the "contributing guidelines" prompt never shows. Same location rule as above; double check exact filename casing on case-sensitive filesystems (Linux) even though GitHub itself is forgiving about case.
  • Checklist items in the template never actually get checked by anyone. A template is a prompt, not an enforcement mechanism — enforcement is Lab 6's required-status-checks/required-reviews, which can be backed by an actual CI job that greps the PR body for a checked box, but the raw Markdown checklist alone is honor-system only.
  • Closes #123 typo'd as Close #123 or referencing the wrong repo's issue number in a fork. GitHub only recognizes the exact keyword forms (Closes/Fixes/Resolves, singular or plural, case-insensitive) — a near-miss silently just becomes inert text with no auto-close behavior, and cross-repo references need the owner/repo#123 form.

Checkpoint

A brand-new PR against this repo shows the template's structure pre-filled in its description, and the repo's "Open a pull request" / "New issue" pages surface a link to the contributing guidelines.

9Demonstrate Git Rebase and Compare It with Merge

Prerequisites & dependencies

  • Lab 5's conflict-resolution fluency — rebase conflicts are resolved with different commands than merge conflicts, and you need the underlying conflict-marker literacy from Lab 5 to not be learning two things at once here.
  • A branch that has diverged from its base (both sides have new commits since they split) — rebase is uninteresting to demonstrate on a branch that's simply behind with no commits of its own.

Concept: what rebase actually does

Given feature branched from main, and both have since gained new commits:

      A---B---C  feature
     /
D---E---F---G  main

Merge creates a new commit H with two parents (C and G), joining both histories exactly as they happened, in the order they happened:

      A---B---C
     /         \
D---E---F---G---H   (main, after merge)

Rebase instead rewrites feature's commits, one at a time, replaying each one's changes (not the original commits themselves — brand-new commits with new hashes are created) on top of main's current tip:

D---E---F---G---A'---B'---C'   (feature, after rebase)

A', B', C' contain the same diffs as A, B, C but are entirely new commit objects — different hashes, because a commit's hash is derived partly from its parent, and the parent changed. This is the single fact that explains every rebase rule that follows: rebase does not modify existing commits, it creates new ones and abandons the old ones, which is only safe when nobody else has already built on top of the old ones.

Step-by-step: rebasing a feature branch

$ git checkout feature/rsvp-list
$ git fetch origin
$ git rebase origin/develop

If a conflict occurs partway through (very possible — same root cause as Lab 5, same markers, different follow-up commands):

# edit conflicted files, resolve markers
$ git add <file>
$ git rebase --continue

Repeat resolve→add→--continue for as many commits as conflict (rebase applies commits one at a time, so you may hit this more than once for a single rebase). Escape hatches:

$ git rebase --abort     # cleanly bail out, back to pre-rebase state, no partial damage
$ git rebase --skip      # drop the current commit entirely instead of resolving it (rare, deliberate)

Once done, because feature/rsvp-list's commits now have new hashes, your local branch has diverged from what you last pushed:

$ git push --force-with-lease origin feature/rsvp-list

--force-with-lease is a safer force-push: it refuses if the remote branch has commits you haven't seen (e.g. a teammate also pushed to your "personal" feature branch since your last fetch), preventing you from blindly clobbering work you don't know about. Plain --force has no such check — never use plain --force as a habit; if the lease check ever legitimately blocks you, git fetch first and look at what changed before deciding to override it.

Interactive rebase (-i) — cleaning up your own commit history before it's shared

$ git rebase -i HEAD~4

Opens an editor listing your last 4 commits, oldest first, each on a line starting with pick. Change the leading word to: - reword — keep the commit's changes, edit its message. - squash (or s) — merge this commit's changes into the one above it, combining messages for editing. - fixup (or f) — like squash, but silently discards this commit's message (keeps the one above's). - drop — remove the commit entirely. - Reordering the lines themselves reorders the commits (careful — only safe if the reordered commits don't depend on each other's changes).

This turns a real working history like wip, fix typo, actually fix the bug, remove console.log into one clean feat(rsvp): add RSVP list validation commit before it's ever seen by a reviewer or merged — a direct enabler of Lab 10's "meaningful commit history" hygiene goal.

The golden rule of rebase

Never rebase a branch that other people have already pulled from and built work on top of. Because rebase creates new commit hashes and abandons the old ones, anyone who already has the old commits now has a history that has silently diverged and irreconcilably conflicts with yours — their next git pull produces a tangled, duplicated mess (or an outright rejected push on their end) rather than a clean conflict. Rebase freely on your own not-yet-shared, or exclusively-yours, feature branches. Never rebase main, develop, or any branch other people are actively also committing to.

Side-by-side comparison

Merge Rebase
History shape Preserves exact branching structure (non-linear) Rewrites into a straight line
Commit hashes Untouched Feature branch commits get new hashes
New commit created Yes, one merge commit (with --no-ff) No merge commit; commits are individually replayed
Safe on shared/public branches Yes, always No — golden rule above
Conflict resolution happens Once, for the whole merge Potentially once per replayed commit
Undo command git merge --abort git rebase --abort
Typical use Integrating a finished feature into develop/main (Lab 4) Cleaning up / updating a feature branch before it's shared or merged
GitHub PR equivalent "Create a merge commit" "Rebase and merge"

Neither is "better" in the abstract — GitFlow (Lab 4) explicitly chooses merge (with --no-ff) for integrating finished features specifically because it wants the branch structure preserved as a permanent record; the same team might still use interactive rebase privately, on their own feature branch, before ever opening the PR, to make that eventual merge diff clean. The two techniques operate at different times, for different audiences (rebase: for you, before sharing; merge: for the team, as the permanent record) — the version students most often get wrong is picking rebase for the team-facing integration step, which then breaks anyone who'd already pulled that branch.

What can go wrong

  • Rebased main (or any shared branch) directly, then pushed force. Every teammate's local main now conflicts with the remote. There's no clean automated fix — coordinate a manual recovery (everyone re-clones or hard-resets to the new main, losing any local-only commits they hadn't pushed). This is the scenario the golden rule exists specifically to prevent; treat it as a "call a team meeting" incident, not a quick command.
  • git push (without --force...) fails after a rebase with "tip of your current branch is behind." Expected — the remote still has the old-hash commits. This is exactly when --force-with-lease is correct to use, because it's your own feature branch (verify that assumption first).
  • Interactive rebase squash/fixup picked the wrong commit to merge into (squash always merges upward, into the commit immediately above its position in the list — order in the editor matters). Abort with git rebase --abort and redo the ordering if it merged the wrong pair.
  • Rebase conflict on the same commit, repeatedly, cycle after cycle. Sometimes it's genuinely faster to git rebase --abort and instead do one clean merge (accepting the non-linear history) than to fight a long rebase with many conflicting commits — know when to cut your losses; rebase is a tool, not a moral obligation.
  • Lost commits after a rebase went wrong and you already closed the terminal / can't remember the old hashes. git reflog records every position HEAD has pointed to on this machine, including pre-rebase, for about 90 days by default — git reflog, find the entry from before the rebase, git reset --hard <that-hash> recovers it. This is the single most valuable "undo almost anything" command in Git and worth memorizing independent of this lab.

Checkpoint

Perform the same logical update twice on two disposable throwaway branches — once via merge --no-ff, once via rebase — and compare the two git log --graph --oneline outputs side by side; be able to explain, out loud, which commit hashes changed and why.

10Implement Repository Hygiene Using Commit Conventions and Code Reviews

Prerequisites & dependencies

  • Everything before this lab, practically speaking — hygiene is the discipline that makes Labs 1–9 sustainable across a team and across months, not a standalone technique.

Concept

"Repository hygiene" is the set of small, cheap habits that keep a growing repo's history, issue tracker, and file tree legible to someone joining in month six instead of month one. None of these are enforced by Git itself except where you wire enforcement in via hooks or CI — they are team discipline, documented (Lab 8) and, where possible, automated.

Conventional Commits

A structured commit message format:

<type>(<optional scope>): <short summary, imperative mood, no trailing period>
<optional longer body — why, not what>
<optional footer — BREAKING CHANGE: ..., Closes #123>

Common types:

Type Meaning
feat a new feature
fix a bug fix
docs documentation only
style formatting, no logic change (whitespace, semicolons)
refactor code change that neither fixes a bug nor adds a feature
test adding/correcting tests
chore tooling, build config, dependency bumps — no production code change
perf a performance improvement

Examples: feat(rsvp): add capacity limit to event signup, fix(auth): correct off-by-one in token expiry check, chore: bump eslint to 9.x.

Two direct payoffs, not just tidiness for its own sake: (1) tools like standard-version or semantic-release can compute the next SemVer number automatically from your commit history — any feat commit since the last release bumps MINOR, any fix bumps PATCH, a footer containing BREAKING CHANGE: bumps MAJOR — directly automating Lab 7's manual judgment calls; (2) changelogs (including GitHub's "Generate release notes" from Lab 7) read as a structured, grouped list instead of an undifferentiated wall of "fix stuff", "more fixes", "wip".

.gitignore — don't track what shouldn't be tracked

# dependencies
node_modules/
venv/
# build output
dist/
build/
# environment / secrets
.env
*.pem
# editor/OS noise
.vscode/
.DS_Store

GitHub's gitignore template collection (offered at repo-creation time, per language/framework) is the right starting point — hand-writing one from scratch invites gaps. A file already tracked before it was added to .gitignore keeps being tracked — .gitignore only affects untracked files going forward; untrack an already-committed file with git rm --cached <file> (Lab 3 covered this for the secrets case specifically).

Git hooks — local automated gatekeeping

Scripts in .git/hooks/ (not version-controlled by default, since .git/ itself isn't committed) that run automatically at points like pre-commit (before a commit is created — good for linting/formatting) or commit-msg (validate the message matches Conventional Commits) or pre-push. Because raw .git/hooks/ scripts aren't shareable via the repo itself, teams standardize with a tool like Husky (JS ecosystem) or pre-commit (Python ecosystem) that installs shared, version-controlled hook definitions for everyone on npm install / pre-commit install. A commit-msg hook rejecting git commit -m "asdf" is how Conventional Commits goes from "please remember to do this" to "structurally can't skip it."

Code review discipline

Beyond the mechanical PR-approval gate from Lab 6, good review culture is about what gets said and how: - Review the diff for correctness, but also for whether it belongs at all — scope creep in a PR ("while I was in there I also refactored...") makes both review and eventual revert harder. - Prefer specific, actionable comments ("this loop is O(n²); a Set lookup here would be O(n)") over vague ones ("this seems slow"). - Distinguish blocking feedback from suggestions — GitHub's review UI itself doesn't enforce this distinction, so teams adopt a comment prefix convention, e.g. nit: for non-blocking style nits, blocking: or no prefix for must-fix. - Small, focused PRs review faster and more thoroughly than large ones — a 40-line diff gets careful line-by-line attention; a 2000-line diff gets a rubber-stamp "LGTM." This is itself a hygiene practice: it argues for smaller feature branches merged more often, which loops back to why GitFlow's feature/* branches should be scoped narrowly. - The reviewer's job is to protect the codebase and teach, not to demonstrate superiority — tone matters as much as correctness for a review culture that people don't come to dread.

Repository-level tidiness checklist

  • A meaningful README.md at the root: what the project is, how to run it, how to contribute (link to CONTRIBUTING.md).
  • A LICENSE file if the repo is or might become public — without one, default copyright law means nobody else has any legal right to use your code, even if the repo is public and readable.
  • Branches deleted after merge (Lab 4's cleanup step), so git branch -a / the GitHub branch list stays a true reflection of active work, not an ever-growing graveyard.
  • Stale/abandoned branches periodically pruned (git fetch --prune, and closing/deleting genuinely dead branches on GitHub).
  • Issues and PRs labeled consistently (bug, enhancement, good first issue) so the tracker itself stays navigable.
  • No secrets ever committed — enforced technically where possible via GitHub's built-in secret scanning (Settings → Code security) in addition to the .gitignore discipline above.

What can go wrong

  • A commit-msg hook rejects everyone's commits because it's too strict (e.g. requires a scope on every single commit, including one-line chore bumps where a scope is meaningless). Tune the hook's rules to match the team's actual usage before treating rejection as "working as intended" — an overly rigid hook trains people to bypass it (git commit --no-verify), which defeats the purpose entirely.
  • git commit --no-verify used routinely to skip hooks "just this once." Once discovered as an escape hatch, it tends to become the norm rather than the exception — pair local hooks with a server-side/CI check (Lab 6's required status checks) that can't be bypassed by a local flag, for anything that truly must be enforced.
  • .gitignore added after secrets/node_modules were already committed and pushed. As covered in Lab 3: .gitignore doesn't retroactively untrack, and if real secrets already reached a public remote, treat them as compromised and rotate them — don't rely on history-rewriting alone as the fix.
  • Conventional Commits adopted inconsistently — some contributors follow it, others don't, and automated changelog/version tooling silently misclassifies or skips the non-conforming commits. Back the convention with the commit-msg hook above, or a CI check on PR titles (common when using squash-merge, since the PR title becomes the squashed commit's message — see Lab 6).
  • Huge, unreviewable PR because feature branches lived too long before merging. Preventive, not curative: shrink the unit of work going forward (smaller feature/* branches, merged more often) rather than trying to review the existing giant diff carefully — nobody reviews a 2000-line diff carefully no matter how much time is allotted.

Checkpoint

Every commit in git log --oneline -10 follows the type(scope): summary convention; .gitignore is present and git status shows no build artifacts or secrets as untracked/trackable; the most recent merged PR shows at least one substantive (non-"LGTM"-only) review comment.

1Print a Message Automatically on Every Push

Prerequisites & dependencies

  • The campus-events repository from Lab 2, cloned locally, with push access already working (Lab 2's PAT/SSH setup).
  • Nothing to install. GitHub Actions runs entirely on GitHub's own servers — your machine's only job in this lab is to git push a YAML file.
  • If you turned on branch protection for main in Lab 6, direct pushes are now blocked — commit the workflow file on a short-lived branch and open a PR (Labs 4 and 6) instead of pushing straight to main. GitHub Actions doesn't care which branch introduces the file, only that it eventually lands on whichever branch the workflow's trigger watches.

Concept

A workflow is a YAML file that tells GitHub "when X happens, run Y." Every workflow breaks down into the same five pieces, and almost every question you'll ever ask about GitHub Actions reduces to "which of these five am I looking at":

Piece YAML key What it means
WorkflownameThe whole automation process — one YAML file is one workflow.
TriggeronThe event that starts the workflow, e.g. a push.
JobjobsA unit of work; a workflow can contain one or more jobs.
StepstepsAn individual task inside a job, run in order.
Actionrun / usesA step either runs a raw shell command, or uses a reusable pre-built action.

A sixth term you'll see constantly but never write directly: the runner — the virtual machine on GitHub's infrastructure that actually executes a job's steps, one job per runner, provisioned fresh and destroyed when the job finishes.

Step-by-step

Workflow files live in one specific place — GitHub only looks in .github/workflows/ at the repository root:

$ cd campus-events
$ mkdir -p .github/workflows

Create .github/workflows/hello.yml:

name: Hello World
on:
  push:

jobs:
  hello:
    runs-on: ubuntu-latest
    steps:
      - name: Print message
        run: echo "Hello Students! GitHub Actions is working."

Commit and push:

$ git add .github/workflows/hello.yml
$ git commit -m "ci: add hello world workflow"
$ git push

On github.com, open the repository's Actions tab. A run named "Hello World" appears within a few seconds — GitHub started it the moment your push landed. Click the run, click the hello job, then expand Print message to see the echoed line in the log.

What can go wrong

  • No run ever appears on the Actions tab. Almost always a path problem — the folder must be exactly .github/workflows/ at the repo root, not github/workflows/, not nested inside a subfolder, not .github/workflow/ (singular). GitHub silently ignores YAML files anywhere else.
  • A red "!" next to the run instead of a normal log. A YAML parse error — almost always inconsistent indentation (YAML is whitespace-sensitive; mixing tabs and spaces, or misaligning steps: under runs-on:, breaks the whole file). Click the failed run for the exact line GitHub couldn't parse.
  • You pushed but branch protection (Lab 6) rejected it. Same GH006: Protected branch update failed message from Lab 6 — open a PR instead, as noted in Prerequisites.
  • The run appears but never finishes, stuck "Queued." Rare on a personal free-tier account, but possible if your organization has disabled Actions, or hit its concurrent-job limit — check Settings → Actions → General for the repo/org.

Checkpoint

The Actions tab shows a completed "Hello World" run with a green check; the "Print message" step's log contains the exact text Hello Students! GitHub Actions is working.

2Check Out and Explore the Repository in a Workflow

Prerequisites & dependencies

  • GHA 1 complete — you have a working .github/workflows/ folder and have seen one green run.

Concept

Here is the fact that trips up almost everyone the first time: a job's runner starts as a completely empty virtual machine. It does not automatically contain your repository, even though the workflow that's running clearly lives inside that repository. GHA 1's hello.yml got away with this because echo needs no files at all — it just prints a literal string.

The moment a step needs to read a file from your repo, the workflow must fetch it explicitly, with the checkout action:

- uses: actions/checkout@v4

uses: is the other half of the run/uses pair from GHA 1 — instead of a raw shell command, it pulls in a reusable, versioned unit of automation that someone else (here, GitHub itself) already wrote and maintains. actions/checkout@v4 clones your repository onto the runner, at the exact commit that triggered the workflow, so every step after it can see your files. It is, in practice, the first step of nearly every real-world job you will ever write.

Step-by-step

Create .github/workflows/explore.yml:

name: Explore Repository
on:
  push:

jobs:
  explore:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Show current directory
        run: pwd
      - name: List repository files
        run: ls -la
      - name: Show message
        run: echo "Repository files are available!"

$ git add .github/workflows/explore.yml
$ git commit -m "ci: add repository explore workflow"
$ git push

Open the new run on the Actions tab and expand List repository files — you'll see README.md and the .github folder itself, proof the checkout step pulled in the real repository content, at the real path the runner cloned it to.

What can go wrong

  • Deleted the checkout step to "save time" and ls -la shows almost nothing. Expected, not a bug — without actions/checkout, the runner's working directory genuinely has no repository in it. This is the single most common first mistake with GitHub Actions, and now you've seen both sides of it on purpose.
  • pwd prints an unfamiliar path like /home/runner/work/campus-events/campus-events. Correct and expected — GitHub nests the checkout under a working-directory convention of work/<repo>/<repo>; you never need to hardcode this path, later steps just work relative to it.
  • Forgot the -a flag and don't see the .github folder. Plain ls hides dotfiles/dot-folders by convention (same as on your own machine) — ls -la is what shows them.

Checkpoint

The "List repository files" step's log shows your actual repository contents (README.md, .github), not an empty directory.

3Run a Python Program Automatically on Push

Prerequisites & dependencies

  • GHA 2 complete — this lab adds one more uses: action on top of the checkout pattern you just learned.

Concept

Runner images (ubuntu-latest and friends) ship with several languages and tools already installed, Python among them — but relying on "whatever version happens to be preinstalled" is fragile, because GitHub updates those default versions over time without asking you. actions/setup-python pins an exact version explicitly, the same discipline Lab 1 applied to core.autocrlf: make the behavior deterministic instead of hoping the environment cooperates.

Notice the with: block under the setup-python step — this is how a uses: action accepts configuration, the same way a function accepts arguments. A plain run: step has no with:, because there's nothing to configure; it's just a shell command.

Step-by-step

Create hello.py at the repository root:

print("Hello from Python!")
print("GitHub Actions executed my program.")

Create .github/workflows/python.yml:

name: Run Python Program
on:
  push:

jobs:
  python:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Run Python program
        run: python hello.py

$ git add hello.py .github/workflows/python.yml
$ git commit -m "ci: run hello.py on push"
$ git push

What can go wrong

  • python-version without quotes. Always quote it — '3.12', not 3.12. Unquoted, YAML parses 3.10 as the number 3.1 (trailing zero dropped, just like ordinary arithmetic notation), silently requesting the wrong Python version. Quoting forces YAML to treat it as text.
  • python: command not found. The Setup Python step was skipped, misordered (must run before the step that uses python), or misspelled as uses: actions/setup-python with no version tag — always pin an @v5-style version on the action itself too.
  • can't open file 'hello.py': No such file or directory. Almost always a missing or misordered checkout step (GHA 2's lesson again) — without it, hello.py was never on the runner in the first place.

Checkpoint

The "Run Python program" step's log shows both printed lines from hello.py.

4Automatically Run Tests on Push and Pull Request

Prerequisites & dependencies

  • GHA 3 complete.
  • Lab 6's branch protection concepts — this lab produces the exact kind of status check that "Require status checks to pass before merging" (Lab 6) was written to gate on.

Concept

Continuous Integration (CI), concretely and without the buzzword haze: every time code changes, an automated process builds and tests it, so a broken change is caught by a machine in minutes instead of by a teammate days later. Everything in GHA 1–3 was CI's plumbing; this lab is the first one that actually behaves like CI, because it adds a second trigger:

on:
  push:
  pull_request:

pull_request matters for a reason that connects directly back to Lab 6: it runs your tests against the proposed merge result of a PR, before anyone approves it — exactly the status check that a branch-protection rule can require to pass before the merge button unlocks. push alone would only test commits after they've already landed on a branch; pull_request tests them while they're still up for review.

Step-by-step

Create test_hello.py:

def add(a, b):
    return a + b

def test_add():
    assert add(10, 20) == 30

Create .github/workflows/tests.yml:

name: Python Tests
on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - name: Install pytest
        run: pip install pytest
      - name: Run tests
        run: pytest

$ git add test_hello.py .github/workflows/tests.yml
$ git commit -m "test: add pytest CI workflow"
$ git push

Watch it pass — then, deliberately, break it. Change the assertion to something false:

    assert add(10, 20) == 31

Commit and push that change and watch the run turn red. This is not busywork — reading a failed CI log calmly, instead of panicking at the red X, is a skill worth practicing on purpose while the stakes are zero.

What can go wrong

  • Tests pass locally but fail in CI. Almost always an environment difference — a package installed locally but not listed for pip install, or a Python version mismatch (compare your local python --version against the workflow's python-version).
  • The workflow doesn't run on your Pull Request. Check the PR's base repository — pull_request runs use the workflow file as it exists on the PR's target branch, not the source branch, for security reasons (so a malicious PR can't rewrite the CI itself to hide a failure).
  • Left the broken assertion in and forgot to fix it. Harmless here since this is a practice repo, but exactly the habit Lab 6's "Do not allow bypassing" setting exists to prevent on a real project — a required, passing status check is what stops this from ever reaching main.

Checkpoint

With the correct assertion, the Actions tab shows a green "Python Tests" run. With the deliberately wrong assertion, it shows a red, failed run — and you can explain, from the log, exactly which line failed and why.

5Chain a Build Job and a Test Job With needs

Prerequisites & dependencies

  • GHA 4 complete.

Concept

Every workflow so far has used exactly one job. A workflow can define several — and by default, GitHub starts them all at the same time, each on its own separate, isolated runner, with no shared state between them. That default is fine when jobs are genuinely independent (say, a lint job and a test job that don't depend on each other's output). It's wrong the moment one job's output is the input to another — a build has to finish before the thing it built can be tested.

needs: is the fix: it tells GitHub "don't start this job until the named job has finished successfully."

test:
  needs: build

One nuance worth knowing even though today's lab doesn't need it: because each job still runs on its own fresh runner, needs: alone only controls timing, not file sharing — a file the build job creates does not automatically appear on the test job's runner. Real pipelines pass files between dependent jobs with the upload-artifact / download-artifact actions; today's two jobs just each echo a message, so there's nothing to hand off yet.

Step-by-step

Create .github/workflows/build-test.yml:

name: Build and Test
on:
  push:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
      - name: Build project
        run: echo "Building project..."

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
      - name: Run tests
        run: echo "Running tests..."
      - name: Test successful
        run: echo "All tests passed!"

$ git add .github/workflows/build-test.yml
$ git commit -m "ci: chain build and test jobs"
$ git push

On the Actions tab, open the run and look at the job graph at the top — build and test are drawn as two connected boxes, not two parallel ones, visual confirmation that needs: took effect.

What can go wrong

  • Removed needs: build and both jobs start simultaneously. Not an error, just the default behavior from Concept above reasserting itself — add the line back.
  • Indented test: under build: by mistake. That nests test as a key inside build instead of a sibling job — YAML will either fail to parse or silently produce a workflow with only one real job. Both job names must sit at the same indentation level, directly under jobs:.
  • Made build deliberately fail (e.g. a bad command) to test the dependency, and test still ran. Shouldn't happen with a plain needs: build — double-check the step that's supposed to fail actually returns a non-zero exit code, and that needs is spelled correctly (a typo like need: is silently ignored as an unrecognized key on some parsers rather than erroring loudly).

Checkpoint

build runs to completion first; only then does test start. If you temporarily break build, test is shown as skipped, not failed — GitHub distinguishes "never ran because its dependency failed" from "ran and failed" in the job graph.

CGlossary

Working directory — the files on disk as they currently exist. Staging area / index — the draft of the next commit; populated by git add. Commit — an immutable, hashed snapshot with author, message, and parent(s). Branch — a movable pointer to a commit; creating one is O(1), not a file copy. HEAD — the pointer to whatever commit/branch you currently have checked out. Remote — a named reference to another copy of the repository (conventionally origin). Fast-forward merge — moving a branch pointer forward with no new merge commit, possible only when the target hasn't diverged. Three-way merge — Git's default merge algorithm, comparing both tips against their common ancestor. Conflict — both sides changed the same lines differently since their common ancestor; needs a human decision. Fork — a full copy of a repository under a different owner's account, the basis for external contributions to repos you don't have write access to. Upstream — conventionally, the original repo a fork was made from (as opposed to origin, your own copy). SemVer — MAJOR.MINOR.PATCH versioning where each segment has a precise, binding meaning. Annotated tag — a full Git object with its own author/date/message, optionally signed; the kind to use for releases. Rebase — replaying commits onto a new base, creating new commit hashes; never do this to shared history. Reflog — a local, time-limited log of everywhere HEAD has pointed; the most reliable "undo" mechanism in Git. GitFlow — a branching convention with main, develop, feature/*, release/*, hotfix/*. Conventional Commits — a type(scope): summary commit message convention enabling automated changelogs/versioning. Workflow — a YAML file in .github/workflows/ defining an automated process and what triggers it. Job — a unit of work within a workflow, running on its own isolated runner. Step — a single task inside a job, either a run command or a uses action. Runner — the virtual machine, provisioned fresh per job, that executes a job's steps. Action — a reusable, versioned unit of automation invoked with uses:, e.g. actions/checkout. Continuous Integration (CI) — automatically building and testing code on every change, so breakage is caught by a machine within minutes.
